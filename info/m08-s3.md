# Amazon S3

**Handout.** Region: **ap-south-1** (Mumbai).

You store the invoice as an object. You create bucket `sample-orders-invoices-ACCOUNTID` and, if it does not exist, role `sample-create-order-role`. You do not create a replication rule or a bucket in `ap-southeast-1`.

## Goals

By the end of this handout you can explain:

1. Buckets, objects, keys, Block Public Access, and the difference between durability and availability.
2. How versioning keeps an overwrite, how to read the previous version, and what a delete marker does.
3. What a lifecycle rule for noncurrent versions does, and how SSE-S3 differs from SSE-KMS.
4. How a bucket policy grants the Sample Orders role object access, and how RTO and RPO apply to an invoice object. Cross-region replication is explained here and left unbuilt.

## Fundamentals and data protection

S3 stores **objects** in a **bucket**. An object is bytes plus metadata and a **key**. The key is the name. Sample’s invoice might be `invoices/ord-1001.txt`. The bucket name is global, so include the 12-digit account id: `sample-orders-invoices-ACCOUNTID`.

The bucket is created in **ap-south-1**. The object does not automatically exist in Singapore. The application uses the API: `PutObject`, `GetObject`.

**Durability** is the chance the bytes are not lost. S3 is designed for very high durability of objects you have stored. **Availability** is the chance you can read them right now. A regional outage is an availability problem. Versioning and replication prepare you for deletion and for region loss. They are not the same knob.

**Block Public Access** stays **on**. All four public-access blocks. A public invoice bucket is a design flaw. Leave object ownership as “bucket owner enforced,” which disables ACLs, when the console offers it.

The invoice is not a substitute for the Aurora row. The row is what the API and the packing service query. The object is the document a customer downloads. Losing one is not the same incident as losing the other.

## Versioning

Versioning is a bucket setting. When it is on, a put to an existing key adds a new **version id**. The previous bytes remain. A GET without a version id returns the **current** version.

Write `version one`, then `version two`, under the same key. Both version ids remain. You can GET the older version, or copy it so it becomes the new current version.

A delete without a version id does not remove the bytes when versioning is on. It adds a **delete marker**, which becomes current, and GETs look like the object is gone. The older versions remain until a lifecycle rule or a delete-by-version-id removes them. Permanent delete is a delete that names the version id.

Suspending versioning later does not delete old versions. It stops new ones. Leave versioning on for this bucket.

## Lifecycle

A lifecycle rule is a policy the bucket applies over time. Two actions matter:

- **Transition** moves an object to a colder storage class after a number of days. Colder classes cost less to store and more to retrieve. Invoices that nobody reads after 90 days are the usual example. A transition rule on a one-line practice file adds noise.
- **Expiration** deletes. For a versioned bucket, expire **noncurrent versions** after 30 days so an overwrite does not keep every invoice revision forever. You can also expire delete markers that are the only thing left.

Create one rule: expire noncurrent versions after **30 days**. Do not wait 30 days, and do not add a transition.

Lifecycle is not a backup. An expiration rule that is too aggressive destroys the copy you meant to keep. Read the rule before you save it.

## Encryption

Every new object should be encrypted. **Default encryption** on the bucket applies when the put does not ask for something else.

- **SSE-S3** (AES-256, key managed by S3) is the default for this bucket. No key policy to write.
- **SSE-KMS** uses a KMS key. You can use the AWS-managed key `aws/s3` or a customer-managed key. A customer-managed key lets you edit the key policy and see KMS calls in CloudTrail. It is the right production conversation when you must revoke a key or restrict who can decrypt. It is extra surface for a first invoice. Know the difference. You do not need a customer-managed key for this bucket.
- **Client-side encryption** means the application encrypts before the put. AWS stores opaque bytes. Sample Orders does not encrypt invoices in the application.

TLS protects the upload on the wire. Default encryption protects the object at rest. You want both. A bucket policy can deny puts that do not use TLS (`aws:SecureTransport`). That statement is optional.

## Bucket policies

A **bucket policy** is a resource policy. It sits on the bucket. An **IAM policy** sits on a user or a role. In the same account, a put succeeds when the identity’s IAM policy allows it and no explicit deny applies. A bucket policy Allow for the role documents the application’s access. It does not, by itself, stop another IAM principal in the account who also has `s3:PutObject`.

An Allow for the role is not the same as “only the role can write.”

To exclude other principals you need an **explicit deny**, or those principals must not have an IAM allow. An explicit deny for `Principal: *` is easy to get wrong. A mistake can lock you out of the bucket, including out of deleting it. Do not save a deny-all while you are learning the JSON. The saved policy is an Allow for `sample-create-order-role`.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCreateOrderRole",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::ACCOUNTID:role/sample-create-order-role"
      },
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::sample-orders-invoices-ACCOUNTID/*"
    }
  ]
}
```

The role must exist before you save this, or the console rejects the principal. Create `sample-create-order-role` with a Lambda trust policy and **no** S3 admin policy. The bucket policy grants the role access to this bucket’s objects. The role does not need `s3:*` on `*`.

Block Public Access still blocks a statement that grants `Principal: *`. Leave the blocks on.

`s3:GetObject` and `s3:PutObject` do not include `s3:DeleteObject` or `s3:ListBucket`. Listing is a bucket-level action on `arn:aws:s3:::bucket-name`, not on `/*`. An upload from the console uses your own IAM user. The policy on the bucket is the role’s grant.

## Versioning and cross-region replication

**Cross-region replication (CRR)** copies objects to a bucket in another region. Sample’s diagram target is a bucket in **ap-southeast-1**. Replication needs versioning on both buckets and an IAM role that S3 assumes to read the source and write the destination.

What the copy does:

- New versions are replicated after the rule exists. Objects that were already in the bucket are not copied unless you run a separate batch replication.
- Replication is asynchronous. There is a lag. A GET in Singapore immediately after a put in Mumbai can miss.
- Delete markers and specific version deletes replicate only if you configure that. A delete in Mumbai can leave a copy in Singapore. That may be what you want for recovery.
- Encrypted objects replicate only if the destination and the key policy allow it. SSE-S3 is the simple case. SSE-KMS needs extra grants.

CRR is for region loss and for putting a copy closer to another reader. It does not replace versioning inside Mumbai. An overwrite that replicated will overwrite the destination too, once the new version replicates. The previous version remains if versioning is on in both places.

If Mumbai is unavailable, versioning in Mumbai is unavailable with it. A replica in `ap-southeast-1` is the extra control. Design it before you create it. A rule pointed at a second bucket starts inter-region traffic and a second bucket to clean up.

## RTO and RPO

These terms belong to the invoice first. Disaster recovery applies them to the whole system.

- **RPO, recovery point objective:** how much recent work you can afford to lose. For an overwrite in a versioned bucket, the previous version is still there, so the RPO for “I saved the wrong bytes” can be near zero if someone restores that version. For a regional outage, the RPO of CRR is the replication lag. Writes that had not replicated yet are the loss window.
- **RTO, recovery time objective:** how long you can wait before the object is readable again. Downloading a previous version is a short RTO. Reading from another region requires the replica to exist and the application to know the other bucket’s name.

Four architecture patterns use the same words later: backup and restore, pilot light, warm standby, and active-active. They describe whole architectures. They are not S3 storage classes.

## In the console

### 1. Create the bucket

1. Region **ap-south-1**. Note the account id.
2. **S3** → **Create bucket**.
3. Name `sample-orders-invoices-ACCOUNTID`. Region Asia Pacific (Mumbai).
4. Block all public access: **on**.
5. Versioning: **enable**.
6. Default encryption: **SSE-S3**.
7. Create the bucket.

**If the name is taken:** the account id was mistyped, or an old bucket remains. Keep the account id in the name.

### 2. Overwrite and restore

1. Upload `invoice.txt` with body `version one`.
2. Upload `invoice.txt` again with body `version two`.
3. Open the object → **Versions**. Two version ids. The current one is `version two`.
4. Download or open the noncurrent version and read `version one`.

**Expected:** two versions, current body is the second upload.

**If Versions is missing:** versioning is off. Enable it and upload again. The first object may have a null version id.

### 3. Lifecycle and policy

1. Management → **Lifecycle rules** → create a rule named `expire-noncurrent-invoices`.
2. Scope: the whole bucket is acceptable for this exercise.
3. Action: expire noncurrent versions after **30** days. Do not add a transition.
4. Create the role `sample-create-order-role` if needed (Lambda trust, basic execution only).
5. Permissions → **Bucket policy**. Paste the Allow statement above with the real account id and bucket name. Save.

**If the policy fails to save:** the role ARN does not exist, or the JSON has a trailing comma. Fix the ARN. Do not turn off Block Public Access.

### 4. Sketch replication

Source bucket in `ap-south-1`, destination in `ap-southeast-1`, versioning on both, lag between them. Do not create the destination.

## When you are done

1. Empty the bucket. Delete **versions and delete markers**, not only current objects. A versioned bucket that looks empty still bills if versions remain.
2. Delete the bucket.
3. Delete `sample-create-order-role` if this exercise created it and nothing else uses it.
4. Confirm you have no bucket in `ap-southeast-1`.

Keep Block Public Access on. Do not save a deny statement that locks the bucket. One shared key `invoice.txt` makes the overwrite easy to see. Do not enable replication to watch the button.

## What this costs

One small text object is negligible. Versioned debris and a forgotten replication destination are not. Empty all versions, delete the bucket, and do not leave a bucket in the second region.
